# 04. AIco 使いこなしガイド・FAQ

## 概要

AIco の基本的な考え方（4 種の管理情報の使い分け、ブランチのルール、レビューの流れ）と、使い始めによくある疑問・トラブルシュートをまとめています。  
細かいディレクトリ規約やスクリプト引数の全仕様が必要な場合は、AIco 本体リポジトリの `docs/03.spec/` を参照してください。

## 1. AIco の基本スタンス（人と AI の役割分担）

AIco では「どこまで AI に任せ、どこで人間が止まって判断するか」をあらかじめ決めています。

* **AI が主導すること**：現状調査、記録の作成、計画案づくり、実装、テスト検証、独立レビューの段取り、次アクションの案内。
* **必ず人間が決めること**：
  1. **着手合意（DoR）**：この目的・受け入れ条件（AC）・委任範囲で始めてよいか。
  2. **仕様の矛盾・判断分岐**：想定外の課題が見つかったときの方向性。
  3. **レビュー指摘の採否（トリアージ）**：どの指摘を直し、どの指摘を見送るか。
  4. **完了承認（DoD）**：受け入れ条件と検証結果が十分か。

すべての作業を人間が手取り足取り指示する必要はありません。節目で AI が出してくる確認ポイントに答えるだけで、安全かつ再現性高く進められます。

## 2. 4 種の管理情報の使い分け

`management/` 配下には性質の異なる 4 種類の記録を置きます。迷ったときは次の表で選んでください。

| 記録種別 | こんな時に使う | 特徴 |
| :--- | :--- | :--- |
| **議事録**（`02.discussions/`） | まだ仕様やタスクが固まっていない相談・壁打ち | ゴール未定でも始められ、相談だけで終えてもよい |
| **ADR**（`03.adr/`） | 今後の複数作業に影響する重要な設計判断 | 「なぜこの方式を選び、何を却下したか」を長期保存する |
| **チケット**（`04.tickets/`） | 明確なゴールのある開発・修正・調査作業 | 作業ブランチを切り、計画・実装・レビュー・完了まで管理する |
| **Runbook**（`05.runbooks/`） | 繰り返し実施する定常作業（点検・更新など） | 手順書を再利用し、毎回の結果を実施記録として残す |

## 3. ブランチのシンプルなルール

チームや複数セッションで一覧ファイルが競合しないよう、更新場所を 2 つに分けています。

* **統合ブランチ（`main` や `develop`）**：議事録・ADR・Runbook・チケットの起票・全体一覧（`management/index.md` など）の更新。
* **作業ブランチ（`feature/<チケットID>` など）**：そのチケットの計画（`plan.md`）・成果物・レビュー記録・完了確定。**作業ブランチ上で全体一覧は更新しません。**

※作業ブランチが統合ブランチへマージされたあとに一覧を再生成することで、マージ競合を防ぎながらダッシュボードを最新に保てます。

## 4. 独立レビューとトリアージの考え方

実装した AI 自身にそのまま「問題ない？」と聞くと、自分の前提に引っ張られて見落としやすくなります。  
そのため AIco では次の流れでレビューを回します。

1. **`aico-review`**：作成担当とは独立したコンテキストのワーカーへレビューを委譲し、指摘をファイルとして残す。
2. **`aico-review-triage`**：人間が指摘を見て「採用（修正する）／見送り（直さない）」を決める。見送り理由も残るため、同じ指摘が何度も蒸し返されにくい。
3. **`aico-review-fix` → `aico-review-recheck`**：採用分を修正し、再度独立ワーカーが実物照合して解消を確認する。

### 人間レビュー指摘の記録と複数ラウンド運用

作業中や成果物確認時に人間が直接指摘を見つけた場合は、`/aico-review` の人間レビュー記録モードで最初から採用済み（`status: in-progress`）として記録し、トリアージを省いてすぐ `aico-review-fix` へ進めます。  
また、人間指摘の修正・再確認が完了したあとで同一フェーズ内に独立 AI による追加ラウンドレビュー（`re-reviewing` → `reviewing` → `aico-review`）を重ねる運用も正規手順としてサポートしています。

## 5. 並列運用と `git worktree` の実践（任意）

複数のチケットを同時並行で進めたい場合でも、AIco は **「全体一覧（`management/index.md` 等）は統合ブランチ上でのみ更新する」** 設計になっているため、作業ブランチ同士で管理ファイルが競合しにくくなっています。

* **ブランチ切り替えの手間を減らす `git worktree`**：別チケットを同時に開いて並列に AI セッションを回したい場合は、Git の `worktree` を使うと作業ツリーを汚さずに並行作業できます。

```bash
# 例：統合ブランチでチケット起票後、別ディレクトリへ作業ブランチを展開する
git worktree add ../myproj-ticket-b feature/20261125-120000-ticket-b

# 作業・マージが終わったら worktree を片付ける
git worktree remove ../myproj-ticket-b
```

* **マージ時の注意点**：並列で進めたチケットを統合ブランチへ取り込んだら、統合ブランチ側で `tools/aico.sh rebuild_indexes` を実行して一覧とダッシュボードを最新化してください。

## 6. CI への `doctor.py` 組み込み（任意）

AIco の整合性チェック（`management/scripts/doctor.py`）は、必要に応じて GitHub Actions や GitLab CI へ組み込むこともできます。導入すべきかどうかはプロジェクトの運用形態に合わせて判断してください。

* **CI に組み込まなくてよいケース**：個人開発でローカルマージ中心、かつ AI 作業の最後に手元で `tools/aico.sh doctor` を回している場合（追加の CI 実行コストに見合いにくいため任意です）。
* **CI 組み込みが有効なケース**：複数人チームで PR/MR ベース開発をしている場合や、人間による管理記録の手編集・複数ブランチのマージが頻繁に発生する場合（AI を通さない編集でのリンク切れ・同期漏れ・未チェック AC でのクローズを機械的に防げます）。

### GitHub Actions の最小構成例

`.github/workflows/aico-doctor.yml` として配置します（警告も失敗扱いにしたい場合は `--strict` を追加します）。

```yaml
name: AIco Doctor
on:
  pull_request:
  push:
    branches: [main, develop]
jobs:
  doctor:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: python3 management/scripts/doctor.py
```

### GitLab CI の最小構成例

`.gitlab-ci.yml` へジョブを追加します。

```yaml
aico_doctor:
  image: python:3.11-slim
  variables:
    GIT_DEPTH: 0
  before_script:
    - apt-get update && apt-get install -y --no-install-recommends git && rm -rf /var/lib/apt/lists/*
  script:
    - python3 management/scripts/doctor.py
```

> ※ `--strict` を併用する場合は `WARN` も失敗扱いとなるため、CI 環境へ `uv` を導入し、あわせて `management/aico-manifest.json` の `worker_models`（および利用する場合は `pr_template` 実ファイル）を設定しておく必要があります。

## 7. よくある質問（FAQ）・トラブルシュート

### Q1：`tools/aico.sh doctor` で `worker_models` の `WARN` が出ました

エラーではなく「まだ個別モデルを指定していない」というお知らせです。  
未設定のままでも各ツールの既定モデルでそのまま動作します。役割ごとにモデルを使い分けたいタイミングで [おすすめ `worker_models` 設定例](05.worker-models.md) を参考に `management/aico-manifest.json` を編集し、`tools/aico.sh sync_agents` を実行してください。

### Q2：導入時に「未コミット変更があるため停止します」と出ました

安全のため、`install.py` は作業ツリーがクリーンな状態で実行する仕様です。  
作業中の変更を `git commit` または `git stash` してから再実行してください（どうしても未コミット変更を残したまま試したい場合のみ `--allow-dirty` を付けられます）。

### Q3：導入時に「既存の `CLAUDE.md` に独自記述が含まれています」と出ました

AIco では共通規約の窓口を `AGENTS.md` へ一本化し、`CLAUDE.md` は `@AGENTS.md` のみを記載する構成にしています。  
既存の `CLAUDE.md` に書いてあったプロジェクト固有ルールを `AGENTS.md`（マーカー外）へ移してから再実行してください。

### Q4：AI エージェントが `aico-*` スキルを認識してくれません

まず `tools/aico.sh doctor` を実行し、利用しているツールが `management/aico-manifest.json` の `tools` に含まれているか確認してください。  
不足しているツールがある場合は `tools/aico.sh init` で対象ツールを追加し、IDE や CLI を再読み込みしてから確認してください。

### Q5：途中で別セッションや別ツールへ切り替えたいときは？

AIco は進捗を会話履歴ではなくファイル（`index.md`・`plan.md`・`review/`）へ残しています。  
新しいセッションで `/aico-ticket-status` を実行すれば、実物照合によって現在地と次にやるべきスキルをそのまま案内してくれます。

### Q6：プロジェクト独自のルールやスキルを追加したいときは？

* **プロジェクト固有の規約・上書き方針**：`AGENTS.md` の `<!-- AICO:BEGIN -->` 〜 `<!-- AICO:END -->` の**外側**へ記載してください。
* **プロジェクト独自のスキル**：`.agents/skills/` に `aico-` で始まらないフォルダ名（例：`myproj-deploy`）で追加し、`tools/aico.sh sync_agents` を実行すると各ツールへ同期され、AIco アップデート時も保護されます。

### Q7：PR/MR テンプレートが複数あるプロジェクトではどうすればよいですか？

`aico-manifest.json` の `pr_template` は空欄（`""`）のままにしておき、`aico-ticket-pr` を使わずに運用していただいて問題ありません（`aico-ticket-pr` は完全オプショナルであり、使わなくても AIco の全ワークフローは完結します）。  
もし特定のテンプレートで文面生成だけ頼みたい場合は、`/aico-ticket-pr` 実行時に「`.gitlab/merge_request_templates/Bug.md` に沿って作成してください」のようにファイルパスを明示指定してください。

### Q8：`doctor.py` で `done` チケットの未チェック AC や `cancelled` 指摘の理由空欄が `ERROR` になりました

AIco の品質ゲートとして、完了済み（`status: done`）チケットの `## AC（受け入れ条件）` に未チェック（`- [ ]` / `* [ ]`）が残っている場合、および見送り（`status: cancelled`）のレビュー指摘で `## 採否判断（人間選別）` が空欄の場合は `ERROR` になります。  
未完了の AC を確認して達成済みなら `[x]` へ更新（人間受け入れ判断済みの項目も DoD へ根拠を明記して確定）し、見送り指摘には判断理由を簡潔に追記してから再度 `tools/aico.sh doctor` を実行してください。
