# aico-ticket-design

## 目的

`plan.md` の合意仕様にもとづき、プロジェクト資産側のシステム設計書・仕様書を作成または更新し、必要な設計判断を記録する。

## 入力

* 対象チケット ID（省略可）
* 対象 ID の指定が省略された場合は、以下の3段階フォールバックで解決する。
1. ユーザーの明示指定（ID・`slug`・パス）。
2. `uv run <管理ルート>/scripts/ticket_status.py --json` による現在の Git ブランチと `branch` 属性の照合。
3. 自動特定できない場合は該当状態の候補一覧を提示して人間に選択してもらう。

## 前提条件

* 対象チケットの作業ブランチ上であること。
* 対象チケットの状態が `status: in-progress`・`phase: design`・`phase_status: working` であること（異なる場合は現在状態と差分を提示し人間承認を得る）。

## 手順

1. `plan.md` に沿って設計作業を実施し、プロジェクト資産側の設計書・仕様書を作成・更新する（複雑な設計比較や設計書ドラフトは `worker-high`、一般設計書の更新は `worker-middle` へ積極委譲する）。  
   サブエージェントワーカーへ委譲する際は、親セッションの会話履歴が引き継がれない前提で、必ず以下の5項目をプロンプトへ明示する。
1. 参照する手順書・スキルパス
2. 対象範囲（ファイル・調査対象・比較基点コミット等）
3. 入力条件・制約（前提条件・対象外・守るべき規約）
4. 変更可否（読み取り専用か、許可する編集範囲はどこか）
5. 期待する成果と報告形式（出力先パス・実行環境・未確認事項を含む）
2. 複数作業へ影響する重要な設計判断が生じた場合は ADR 化（`aico-create-adr`）を提案し、個別判断は `plan.md` の `## 判断ログ` へ記録する。
3. `plan.md` の該当ステップを `- [x]` に更新し、設計内容について人間へ提示して承認を得る。
4. 設計レビューを行う（`design / reviewing`）か実装へ進む（`implementation / working`）かを人間と合意し、`update_frontmatter.py` と `index.md` の `## 現在地` を更新する。
   ```bash
   uv run <管理ルート>/scripts/update_frontmatter.py --file <チケットindex.md> --set phase=<合意phase> --set phase_status=<合意phase_status> --json
   ```

## 完了条件と状態更新

* 設計書が更新され人間承認を得ていること。
* 合意に応じて `design / reviewing` または `implementation / working` へ更新されていること。

## 報告形式

* 更新した設計書・仕様書一覧
* 判断ログ・ADR 提案の要点
* 更新後の状態と次スキル案内
