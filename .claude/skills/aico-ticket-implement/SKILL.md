# aico-ticket-implement

## 目的

`plan.md` および設計内容に沿って実装とテスト検証を完了し、AC（受け入れ条件）の達成状況を確認する。

## 入力

* 対象チケット ID（省略可）
* 対象 ID の指定が省略された場合は、以下の3段階フォールバックで解決する。
1. ユーザーの明示指定（ID・`slug`・パス）。
2. `uv run <管理ルート>/scripts/ticket_status.py --json` による現在の Git ブランチと `branch` 属性の照合。
3. 自動特定できない場合は該当状態の候補一覧を提示して人間に選択してもらう。

## 前提条件

* 対象チケットの作業ブランチ上であること。
* 対象チケットの状態が `status: in-progress`・`phase: implementation`・`phase_status: working` であること（異なる場合は現在状態と差分を提示し人間承認を得る）。

## 手順

1. `plan.md` のステップ一覧に従って実装と検証を進め、完了したステップを `- [x]` へ更新する。独立した実装・テストは `worker-middle`、定型実装・テスト実行・ログ抽出は `worker-low`、難所の原因分析・バグ切り分けは `worker-high` へ積極委譲する。  
   サブエージェントワーカーへ委譲する際は、親セッションの会話履歴が引き継がれない前提で、必ず以下の5項目をプロンプトへ明示する。
1. 参照する手順書・スキルパス
2. 対象範囲（ファイル・調査対象・比較基点コミット等）
3. 入力条件・制約（前提条件・対象外・守るべき規約）
4. 変更可否（読み取り専用か、許可する編集範囲はどこか）
5. 期待する成果と報告形式（出力先パス・実行環境・未確認事項を含む）
2. テストエビデンスや生ログを保存する必要がある場合は、導入先運用に従いチケット配下の `artifacts/` へ格納する。
3. 仕様矛盾や前提崩れを検知した場合は作業を止め、判明した事実・推奨案先頭の番号付き Markdown 選択肢を提示して人間へエスカレーションする。また、作業中に発見したスコープ外の課題や不具合はその場で修正せず別チケット起票を提案し、検証コマンドが成功する前に完了チェック（`- [x]`）を入れたりテスト削除・無効化で通したりしない。
4. AC に対する検証結果（確認した実行環境と未確認事項を明示）を人間へ報告し、実装レビューを行う（`implementation / reviewing`）かクロージングへ進む（`closing / working`）かを合意する。
5. `update_frontmatter.py` で合意した状態へ更新し、`index.md` の `## 現在地` を更新する。
   ```bash
   uv run <管理ルート>/scripts/update_frontmatter.py --file <チケットindex.md> --set phase=<合意phase> --set phase_status=<合意phase_status> --json
   ```

## 完了条件と状態更新

* 計画ステップの実装・検証が完了し、検証結果（実行環境・未確認事項）が人間へ報告されていること。
* 合意に応じて `implementation / reviewing` または `closing / working` へ更新されていること。

## 報告形式

* 完了ステップ一覧
* テスト・検証結果（実行環境・未確認事項を区別して明記）
* 更新後の状態と、次のアクションを推奨案先頭の番号付き Markdown 選択肢（2〜4件）で案内する（`aico-review` / `aico-ticket-close` 等）
