# design: 0008 文脈に応じた「マスター」「原本」への用語統一

> これは本 Item による変更分の設計であり、全体のマスターは docs/architecture/ にある。
> Item 完了時に、この内容を docs/architecture/ へ反映する。

## 変更の概要

旧語（Unicode: U+6B63 U+672C）の用例を棚卸しし、意味に応じて「マスター」または「原本」に修正する。標準管理対象は ai-dev-standard の管理元で更新し、sync によって JotLine に反映する。プロジェクト所有の文書・記録は JotLine 側で更新する。

| 文脈 | 使用する用語 | 例 |
|---|---|---|
| 唯一の本体・最新の基準 | マスター | システム全体の最新設計、基準となるリポジトリ |
| 全体の最新設計を置く文書群 | マスタードキュメント | `docs/architecture/`、その内容を更新する固定 Task |
| コピー・派生物を作成する元 | 原本 | `.agents/skills/` と `.claude/skills/` へ配布する `payload/skills/` |

単語だけの一律置換をせず、各用例を上記の基準で分類する。同じ説明の複製には同じ表現を使う。

## 影響範囲

| 所有者 | 対象 | 更新方法 |
|---|---|---|
| ai-dev-standard | 管理元の README、配布用 payload、雛形、スキル、テストなど | 管理元の作業ブランチで修正する |
| ai-dev-standard | JotLine の manifest に列挙された標準管理対象 | 更新した管理元から sync する |
| JotLine | `docs/architecture/`、`docs/process.md`、既存の Spec・Review・progress・Discussion・ADR、Backlog の Item など | プロジェクト側で文脈に応じて修正する |
| JotLine | `BACKLOG.md` | Item の更新後に backlog-index で再生成する |

AGENTS.md は標準管理領域だけを sync し、プロジェクト固有欄を保持する。既存の記録は用語だけを修正し、日付・ID・状態・チェック・コミット ID・技術的な判断内容を維持する。本 Item と本 Spec も対象とし、旧語の説明が必要な場合は Unicode の符号位置で表記する。

Git の過去の履歴、外部依存、キャッシュは変更しない。

## 構成とコンポーネント

### 1. 管理元と使用箇所の確認

- 確認できた管理元は `/home/sasaki/workspace/20261103-094806-quiet-quartz/ai-dev-standard`。origin は `https://gitlab.sasaki819.mydns.jp/open/ai-dev-standard`。実装時にこの対応、作業ツリー、適用先とのバージョンを再確認する。現在は管理元の VERSION と JotLine の `.ai-standard-version` がともに 0.1.2。
- JotLine は `feature/0008-replace-seihon-terminology` で作業する。管理元も専用の feature ブランチで作業し、既存の利用者の変更を混在させない。
- Git 管理対象のテキストを隠しパスも含めて検索する。検索結果を読んで用語を分類し、管理元の manifest と JotLine の manifest から更新元を特定する。
- 標準スキルの配布元は `payload/skills/`、通常の配布資材は `payload/<配布先パス>`、manifest の配布元は管理元直下の `manifest.txt`。`payload/docs/architecture/README.md` など初期生成用の資材も管理元の検索対象に含める。

### 2. 管理元の更新と同期

1. 管理元の用語定義、手順書、雛形、固定 Task 名、スキル、PR／MR テンプレートと関連用例を修正する。配布対象に限らず管理元の README・既存テストなども確認する。
2. 管理元の更新手順に従い VERSION をパッチ更新し、CHANGELOG に用語統一を記録する。実際の版と管理元の変更コミット ID は progress に記録する。タグ作成・公開や他プロジェクトへの sync は本 Item で自動実行しない。
3. 管理元の `bash tests/smoke.sh` を実行し、同期処理と標準チェックの既存テストが成功することを確認する。
4. AGENTS.md の標準管理領域外を退避・比較できるようにし、`bash <管理元>/sync.sh <JotLine> --dry-run` で変更予定を確認する。用語変更とその版情報以外の変更があれば原因を確認し、本 Item に無関係な更新を混ぜない。
5. `bash <管理元>/sync.sh <JotLine>` を実行する。配布先のスキルや雛形を直接編集しない。変更は各リポジトリで別々にコミットし、管理元の変更との対応を progress に残す。

### 3. プロジェクト所有資材の更新

- 文脈を分類した結果に従い、プロジェクト所有の文書・記録を修正する。過去の固定 Task の表記も揃えるが、完了状態や Review の判定は変えない。
- 本 Item のタイトル・概要・受入基準も新しい用語で表現し、旧語の文字列を残さない。ID・slug・ファイルパスは維持する。
- Item の変更後は `bash tools/ai-standard/backlog-index.sh` を実行し、生成された一覧にも旧語が残っていないことを確認する。

### 4. 再生成・再同期の確認

- 更新後の雛形から一時ディレクトリに Item・Spec の文書をコピーし、新しい用語で作成できることを確認する。検証用の Item を実際の Backlog に登録しない。
- 同じ管理元から再度 sync して管理対象に差分が生じないことを確認する。AGENTS.md のプロジェクト固有欄が保持され、両方のスキル配布先が一致することも確認する。
- 全文検索は本 Spec を含む新規ファイルも対象にし、最終確認時には新規ファイルを Git の index に含めて検索漏れを防ぐ。

## インタフェース

実行時 API、保存形式、CLI の引数に変更はない。文書に表れる固定 Task の名前と用語定義を「マスタードキュメント」に統一する。パス、Item ID、Review の状態名は変更しない。

## データモデル

アプリケーションのデータモデルに変更はない。標準の適用版情報は既存の `.ai-standard-version` に sync が記録する。新しい管理ファイルや独自の同期経路は追加しない。

## エラー処理

- 管理元が利用できない、管理元の変更と同期先の対応が確認できない、sync が失敗した場合は、その状況を progress に記録し、標準管理対象の直接編集で回避しない。
- 語の意味を分類できない用例は、周辺の文脈を確認する。判断がつかなければその用例を提示して確認し、推測で一括置換しない。
- 同期でプロジェクト固有欄の消失や無関係な変更が見つかった場合は完了扱いにせず、既存変更を保護したうえで管理元と同期手順を確認する。
- 旧語の残存、スキルの不一致、check-docs の失敗があれば、該当する管理元またはプロジェクト所有ファイルを修正して再検証する。

## テスト方針

| 確認 | 方法 | 受入基準 |
|---|---|---|
| 文脈に応じた語の使い分け | 棚卸し結果と最終差分を照合し、意味・状態・履歴情報の維持を確認 | AC1・AC2 |
| 管理元からの反映 | 管理元の差分、smoke テスト、sync の dry-run と実行結果を記録 | AC3 |
| プロジェクト固有欄の保持 | sync 前後の標準管理領域外を比較 | AC4 |
| スキルの一致 | 対応する `.agents/skills/` と `.claude/skills/` を比較し、check-docs でも確認 | AC4 |
| 旧語の残存なし | 管理元と JotLine の双方で Git 管理対象テキストを検索。新規文書を含め0件であることを確認 | AC3・AC5 |
| 再生成・再同期 | backlog-index、雛形の一時コピー、再 sync で旧語が戻らず、再 sync による差分がないことを確認 | AC6 |
| 文書の整合 | `bash tools/ai-standard/check-docs.sh` が成功 | AC7 |

残存検索には、旧語を `chr(0x6B63) + chr(0x672C)` で組み立てて `git grep -nI -F -e <旧語> -- .` に渡す方法を使う。検索用コードやログで旧語を資材へ書き戻さない。git grep の終了コード1は該当なし、0は残存あり、2以上は検索失敗として区別する。

文言修正と既存の生成・同期の検証を対象とし、新規の用語検査ツールは追加しない。アプリの実装・依存関係・ビルド設定は変更しないため、JotLine のビルド・単体テスト・型検査は既存のものを変更せず、実装時に文言以外の変更が必要と判明した場合は検証範囲を見直す。

## 検討した代替案

- JotLine の配布済み資材だけを直接置換する：標準管理ルールに反し、再 sync で旧語が戻るため採用しない。
- 旧語を全て同じ単語に置換する：唯一の基準と派生元の区別が失われるため、文脈ごとに「マスター」「原本」を選ぶ。
- 過去の記録や本 Item を検索対象から外す：承認済み要件の対象範囲と一致しないため採用しない。状態を維持して用語のみ修正する。
- 独自の用語 lint を導入する：今回の範囲では全文検索と再生成・再同期の確認で検証できるため、運用ツールの追加は行わない。
