## Context

- Item 0004 で、JotLine ビューと Markdown エディタの間、および別ファイルの JotLine ビュー同士の間で、カード・スレッド・テキストをドラッグ＆ドロップで移動・コピーできるようにした。移動は2つのファイルにまたがるため、「ドロップ先への追加に成功してから元を削除する」必要がある。
- エディタは Obsidian の内部で CodeMirror 6 が動いている。ドロップ位置への挿入を JotLine が自前で行うには、ドロップ座標から文書上の位置を求める必要があるが、Obsidian の公開 API（`Editor`）にはその手段がなく、CodeMirror の内部（`editor.cm.posAtCoords` など）に頼ることになる。
- Obsidian の公開 API `workspace.on("editor-drop")`（1.1.0 以降）で、エディタへのドロップとドロップ先のファイルは検知できる。CodeMirror 6 は、`text/plain` のドロップを標準でドロップ位置へ挿入する。
- 移動の元を削除するには、ドロップ先で「元の `JotStore`」や「元のエディタと選択範囲」への参照が必要になる。HTML5 の `DataTransfer` には文字列しか入れられず、`dragover` の時点では中身を読めない。
- JotLine の全ビューとエディタは、同じ JavaScript 環境で動く（Obsidian のポップアウトウィンドウも、メインのウィンドウと同じ JavaScript 環境で動く。ただし画面の `document` はウィンドウごとに別）。ポップアウトウィンドウとモバイル版は、動作保証の対象外とした。

検討した方式:

1. エディタへの挿入を自前で行う（`editor-drop` で `preventDefault()` し、CodeMirror の内部 API で位置を求めて `replaceRange`）
2. 挿入はエディタの標準動作に任せ、挿入後のエディタの内容で成功を確かめる
3. 移動の確定を、ドラッグ元の `dragend` の `dropEffect` で判断する
4. ドラッグ元の情報をすべて `DataTransfer` に JSON で入れ、ドロップ先でビューやエディタを探し直す
5. ドラッグ元の情報（参照を含む）を、モジュール内の変数（ドラッグセッション）で共有する

## Decision

- **エディタへのドロップ**: `workspace.on("editor-drop")` で受け、挿入はエディタの標準動作（`text/plain` の挿入）に任せる（方式2）。
  - 移動の場合は、挿入処理の後（`setTimeout(0)`）に、エディタの内容に挿入したテキストが含まれることを確かめてから、元の JotLine ビューのカード・スレッドを削除する。
  - ドロップ先が元と同じファイルなら、`preventDefault()` で挿入を止める。
  - `manifest.json` の `minAppVersion` を 1.1.0 にする。
- **ドラッグ情報の共有**: `src/dnd.ts` のモジュール変数（ドラッグセッション）で、ドラッグ元の種類・ファイル・元を削除するための参照（`JotStore`、`Editor` と選択範囲）を共有する（方式5）。
  - JotLine のカード・スレッドは各コンポーネントの `dragstart` で、エディタの選択テキストは `document` の `dragstart`（キャプチャ段階）で記録する。
  - `DataTransfer` には、エディタや入力欄が使う `text/plain` と、JotLine 由来を示す目印（`application/x-jotline-drag`）だけを入れる。
  - 古いセッションを誤用しないよう、ドラッグ開始のたびにいったん破棄し、ドロップ先では目印の有無やテキストの一致を確かめてから使う。

方式1・3・4を採らなかった理由:

- 方式1：公開されていない CodeMirror の内部 API に依存し、Obsidian の更新で動かなくなるおそれがある。
- 方式3：ドロップ先（エディタ）が `dropEffect` をどう扱うかに依存し、確実でない。
- 方式4：`DataTransfer` には参照を入れられず、ドロップ先でビューやエディタを探し直す処理が必要になり、かえって複雑になる。

## Consequences

良い面:

- Obsidian の公開 API とエディタの標準動作だけで実現でき、内部 API に依存しない。エディタへの挿入の振る舞い（ドロップ位置、アンドゥ履歴）はエディタ本来のものになる。
- ドロップ先は、ドラッグセッションから元の `JotStore` やエディタを直接参照でき、移動の「追加に成功してから元を削除」を単純に実装できる。
- 実装前の想定（エディタの標準の挿入、`preventDefault()` による停止、修飾キーの取得、エディタからのドラッグの検知）は、Obsidian 上で確認済み（Spec 0004 の progress.md の Task 4・Task 6）。

悪い面・制約:

- エディタへの挿入の成功は「エディタの内容に挿入テキストが含まれるか」で確かめるため、ノートにもともと同じテキストがあった場合は、挿入に失敗していても成功とみなす。その場合もノートにはその内容が存在するため、データは失われない。
- エディタの標準動作に任せているため、標準動作が変わると影響を受ける。実際、エディタの選択テキストを JotLine のメイン入力欄へドロップした場合は、ブラウザの標準動作で既定が移動（元のノートから削除）になっており、この振る舞いを仕様として受け入れた。
- エディタからのドラッグ開始は、メインのウィンドウの `document` だけで監視しているため、ポップアウトウィンドウのエディタからのドラッグは検知できない。2026-10-20 に Obsidian 上で確認した結果は次のとおり（ポップアウトウィンドウは動作保証の対象外のまま）。
  - ポップアウトウィンドウのノート → メインウィンドウの JotLine：移動もコピーも行われない（ドラッグを検知できないため、何もしない）。
  - メインウィンドウの JotLine → ポップアウトウィンドウのノート：移動できる（`editor-drop` はポップアウトウィンドウのエディタでも届く）。
  - ポップアウトウィンドウの JotLine と、メインウィンドウの JotLine の間：どちらの向きも移動できる（ドラッグの開始・ドロップを JotLine のコンポーネント自身が処理し、モジュール変数はウィンドウ間で共有されるため）。
  - いずれの場合も、移動後のアンドゥはそれぞれの側で独立して行える。
- Obsidian 1.1.0 より古いバージョンでは、プラグインが読み込まれなくなる。

今後必要になること:

- ポップアウトウィンドウのエディタからのドラッグに対応する場合は、ウィンドウが開かれたとき（`workspace.on("window-open")`）に、そのウィンドウの `document` でも `dragstart` / `dragend` を監視することを検討する（ドラッグセッションはモジュール変数のため、ウィンドウ間で共有済み）。
- Obsidian・CodeMirror の更新で、エディタの標準のドロップ動作が変わっていないかを、更新時に確認する。
